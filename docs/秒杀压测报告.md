# 秒杀并发压测报告

> 对应《需求规格说明书 V1.0.4》验收标准 3（并发压测下无超卖、无重复抢购、库存与订单最终一致）
> 与标准 5（性能达到 NFR-001 目标，以压测报告为准）。
> 被测版本：2026-09-12，更名后的 Jifeng Mall。

## 1 测试目的

| 编号 | 验证目标 | 对应需求 |
| --- | --- | --- |
| T1 | 高并发下**不超卖**：成交数量不超过秒杀库存 | FR-303-2 |
| T2 | **不重复抢购**：同一会员对同一秒杀商品只成功一次 | FR-303-3 |
| T3 | 库存与订单**最终一致**：Redis 与 DB 的库存/已售数吻合，流水号无重复 | FR-304-4 |
| T4 | 抢购提交的响应延迟满足 NFR-001（P95 < 100ms） | NFR-001 |

## 2 测试环境

| 项 | 说明 |
| --- | --- |
| 部署形态 | **Windows 单机单实例**，所有服务、Nacos、MySQL、Redis、RabbitMQ 同机 |
| 应用 | Java 25 / Spring Boot 4.1.1 / Spring Cloud Gateway(WebFlux) / Redis / RabbitMQ |
| 压测发起端 | WSL2 内的 Python 3（`urllib` + `ThreadPoolExecutor`，线程栅栏同步起跑） |
| 请求路径 | 压测机 → 网关 `:8888` → Nacos 负载均衡 → `seckill-api:10021` → Redis Lua |
| 限流 | 网关 Sentinel 对 seckill 路由 500 req/s（本次流量未触及阈值） |

> ⚠️ **这不是生产级压测**：客户端与被测服务在同一台开发机上争抢 CPU，且服务为单实例。
> 数据用于验证**正确性**（T1~T3）是充分的；用于评估**生产性能**（T4）只能作参考，
> 生产环境需要在独立压测机上以集群形态重测。

## 3 测试方法

### 3.1 场景数据

- 秒杀活动 id=1（进行中），秒杀商品 id=1，**库存 50**，每人限购 1 件
- 每轮**注册 200 个压测会员**（`bench_*`），每人只抢一次 —— 这样限购 1 件不会干扰"库存"这一唯一变量

### 3.2 两种起跑方式

| 方式 | 说明 | 考什么 |
| --- | --- | --- |
| **栅栏同步**（并发度 = 会员数） | 200 个线程在 `threading.Barrier` 上对齐，同一瞬间全部发出 | 极端的瞬时洪峰，考验防超卖的原子性 |
| **有界线程池**（并发度 < 会员数） | 固定并发数持续施压 | 稳态负载下的延迟表现，用于对照 NFR-001 |

不同步的话请求会排成队依次到达，**考验不到** Redis Lua 的原子性，所以洪峰场景必须用栅栏。

### 3.3 每轮流程

1. 重置状态：`seckill_good.stock=50, sold=0`；Redis `seckill:stock:1=50`；清空限购标记
2. 并发注册 200 个压测会员
3. 发起 200 次 `POST /api/seckills/grab`，逐笔记录 HTTP 状态、业务码与耗时
4. 轮询 `GET /api/seckill-goods/seckill/1` 等待 MQ 异步下单结算
5. 核对：成交数 / DB 已售数 / DB 剩余库存 / 流水号去重数

## 4 测试结果

### 4.1 正确性（四轮全部通过）

| 并发度 | 请求数 | 成功 | 售罄 7004 | 已参与 7003 | 其他错误 | 成交数 | DB sold | DB stock | 流水号去重 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 10 | 200 | 50 | 150 | 0 | 0 | 50 | 50 | 0 | 50/50 |
| 50 | 200 | 50 | 150 | 0 | 0 | 50 | 50 | 0 | 50/50 |
| 100 | 200 | 50 | 150 | 0 | 0 | 50 | 50 | 0 | 50/50 |
| **200（栅栏同步洪峰）** | 200 | 50 | 150 | 0 | 0 | 50 | 50 | 0 | 50/50 |

| 断言 | 结果 |
| --- | --- |
| T1 成功数 ≤ 库存（防超卖） | ✅ 四轮均为 50 ≤ 50 |
| T1' 成交数 = 库存（防少卖） | ✅ 四轮 `sold` 均为 50 |
| T2 同一会员不重复抢购 | ✅ 无 7003 之外的成功，且 200 会员各只请求一次 |
| T3 DB 剩余库存归零 | ✅ `stock=0` |
| T3 流水号无重复（防重复下单） | ✅ 50 个流水号去重后仍为 50 |
| T3 异步下单结算 | ✅ 每轮均在首次轮询（1.5s 内）完成结算 |

**结论：并发下无超卖、无少卖、无重复下单，Redis 与 DB 最终一致。**

### 4.2 性能

| 并发度 | 墙钟总耗时 | 吞吐 | P50 | **P95** | P99 | max | 均值 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 10 | 292 ms | 684 req/s | 14 ms | **19 ms** | 21 ms | 23 ms | 14 ms |
| 50 | 297 ms | 672 req/s | 41 ms | **75 ms** | 88 ms | 91 ms | 42 ms |
| 100 | 347 ms | 576 req/s | 66 ms | **139 ms** | 198 ms | 236 ms | 73 ms |
| 200（同步洪峰） | 518 ms | 386 req/s | 349 ms | **420 ms** | 436 ms | 439 ms | 337 ms |

**对 NFR-001（秒杀抢购提交 P95 < 100ms）的结论：**

- **并发 ≤ 50 时满足**：P95 = 75ms，吞吐 672 req/s
- **并发 ≥ 100 时不满足**：P95 = 139ms；200 路同步洪峰下达 420ms

延迟随并发近似线性上升，说明瓶颈在**请求排队**而非单笔处理（单笔 P50 仅 14ms）。
本机是单实例 + 客户端同机竞争 CPU 的开发环境；生产上应按 NFR-003 多实例部署并由
Nginx/网关层削峰后再复测。

> 注：需求 9.1 同时提到"秒杀抢购提交 P95 < 100ms"与"秒杀削峰"的设计目标。
> 本次压测验证了**削峰没有牺牲一致性** —— 洪峰下 P95 上升到 420ms，但成交数依然精确等于库存。

## 5 设计有效性分析

从压测结果可以反向确认几处防护确实生效：

| 机制 | 位置 | 压测中的体现 |
| --- | --- | --- |
| Redis + Lua 原子扣减 | `seckill.lua`（库存判断、扣减、限购标记三步在一个脚本里） | 200 路同步洪峰下仍精确成交 50 笔，无一超卖 |
| DB 条件更新兜底 | `seckill_good.stock >= qty` 的条件 UPDATE | 成交数与 DB `sold` 完全吻合 |
| 异步下单幂等 | 以 `seckillNo` 为准，消费者与 order 服务双重幂等 | 50 个流水号无一重复，未产生重复订单 |
| 限购 | Lua 中 `seckill:user:{memberId}:{goodId}` 标记 | 未出现同一会员重复成交 |

## 6 局限与未覆盖项

诚实说明本次压测**没有**覆盖的部分：

1. **单机单实例**，未验证多实例集群下的负载均衡与库存竞争
2. **客户端与服务端同机**，CPU 互相争抢，绝对延迟偏高
3. **只压了抢购提交接口**，未压完整链路（MQ 消费、异步下单、`decreaseStock` 的吞吐上限）
4. **未做长时间稳定性测试**（当前为 4 轮短时压测）
5. **未测超时关单与库存回补在高并发下的表现**（单笔已验证，未做批量）
6. Redis / MySQL / RabbitMQ 均为默认配置，未做参数调优
7. 活动时间窗为演示用 24 小时窗口，未测试活动开始瞬间的缓存预热竞争

## 7 复现方式

```bash
# 前置：13 个服务与 Nacos/MySQL/Redis/RabbitMQ 均已启动，活动处于进行中

# 重置秒杀状态（库存 50、已售 0）
mysql -uroot -p shoplook2026 -e "UPDATE seckill_good SET stock=50, sold=0 WHERE id=1;"
redis-cli SET seckill:stock:1 50

# 洪峰场景（200 路栅栏同步）
python3 seckill_bench.py

# 稳态场景（指定并发度）
python3 seckill_bench.py 10
python3 seckill_bench.py 50
python3 seckill_bench.py 100
```
