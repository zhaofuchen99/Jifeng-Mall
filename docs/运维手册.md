## 1 系统概览（运维视角）

| 项 | 值 |
| --- | --- |
| 服务数 | 13（12 个业务 api + 1 个网关） |
| 前端 | 2 个（前台 `mall-web`、后台 `admin-web`），由 Nginx 托管静态产物 |
| 入口 | Nginx `:8090`（前台）/ `:8091`（后台）→ 网关 `:8888` |
| 中间件 | MySQL 3306 / Redis 6379 / RabbitMQ 5672 / Nacos 8848+9848 |
| 数据表 | 23 张 |
| 运行期目录 | `d:/shoplook2026/upload/`（上传）、`d:/shoplook2026/web/{mall,admin}`（前端产物） |

### 1.1 关键特征（直接影响运维方式）

1. **服务无状态**：业务数据全在 MySQL，秒杀状态与令牌在 Redis，
   异步任务在 RabbitMQ。因此服务可随意重启、可横向扩容。
2. **秒杀状态是「Redis 为主、DB 兜底」的双写结构**，两者可能短暂不一致，
   但有条件更新兜底不会超卖。**巡检时要同时看两边**。
3. **网关 fail-closed**：权限判定调不通时**拒绝**请求（返回 503 而非 403）。
   这是有意的 —— 但意味着 **rbac-api 挂掉会导致全部后台接口不可用**。
4. **两处原本「静默失败」的任务已分别于 2026-09-15 修复**（第 6 章详述）：
   秒杀预热在活动过期时不再静默、超时关单新增了兜底扫描。
   但**第 9 章风险清单里仍有若干未解决项**，接手前先读那一节。

## 2 日常巡检

### 2.1 现状：没有健康检查端点

**项目未引入 `spring-boot-starter-actuator`，没有任何 `/actuator/health` 端点。**
第 2.3 节给出替代方案（进程/端口/业务探针三层）。

### 2.2 巡检清单

| 频次 | 项 | 方法 | 期望 |
| --- | --- | --- | --- |
| 每次重启后 | 端口 | 见 §2.3 | 15 个端口 LISTENING |
| 每次重启后 | 服务注册 | Nacos 控制台「服务列表」 | 13 个实例，命名空间 `jifeng-mall` |
| 每日 | 网关连通 | `curl .../api/goods?pageNo=1&pageSize=1` | 统一 `JsonResp` |
| 每日 | 秒杀库存 | §2.4 一致性核对 | Redis 与 DB 相等 |
| 每日 | 磁盘 | 上传目录与日志目录大小 | — |
| 每次运维操作前 | 数据基线 | `tools/verify/sql/reset_to_baseline.bat` | 打印各项期望值 |

### 2.3 三层健康检查（替代 actuator）

**第一层：进程与端口**（从 Windows 侧看，**不要用 WSL 探端口**）

```bat
netstat -ano | findstr LISTENING | findstr /R ":8888 :1001 :1002 :8090 :8091"
tasklist /FI "IMAGENAME eq java.exe"
```

> ⚠️ **WSL 里往宿主机 IP（`172.22.96.1`）做 TCP 探测不可靠** —— Windows 防火墙会
> 静默拦截，连 445/135 这类常开端口都显示 closed，**会误判成「服务全挂了」**。
> 判服务存活一律从 Windows 侧看监听表。

**第二层：注册中心** —— Nacos 控制台 `http://localhost:8848/nacos`：
- 「服务列表」应见 13 个实例；
- 实例的**健康状态**能反映服务心跳，比端口更能说明「服务是否真的可用」；
- ⚠️ `10007` 端口是 `NeatDM.exe`（联想下载器）占用的，**不是本项目服务**，别被误导。

**第三层：业务探针**（最终判据）

```bat
curl http://localhost:8080/api/goods?pageNo=1&pageSize=1        REM 应返回 JsonResp
curl http://localhost:8090/                                      REM 应 200 text/html
curl -o nul -w "%%{http_code}" http://localhost:8090/api/regions?pageNo=1^&pageSize=0
```

### 2.4 秒杀数据一致性核对

秒杀状态是双写的，巡检时要**同时看两边**：

```sql
-- DB 侧
SELECT id, stock, sold FROM seckill_good;
```
```bat
REM Redis 侧
redis-cli GET seckill:stock:1
redis-cli --scan --pattern "seckill:user:*"
redis-cli --scan --pattern "seckill:order:*"
```

| 检查项 | 期望 |
| --- | --- |
| `seckill:stock:{id}` 是否存在 | 活动进行中时必须存在；缺失会导致抢购全部 7004 |
| Redis 库存 vs DB `stock` | 两者应相等（预热写入 DB 剩余库存，成交同步扣减） |
| `seckill:user:*` 数量 | 应等于「当前持有未关闭秒杀订单的会员数」；只增不减说明回补没释放名额 |
| 订单表 `seckill_no` 去重数 | 应等于秒杀订单数，出现重复说明幂等失效 |

## 3 监控

### 3.1 现状与缺口（如实记录）

| 能力 | 现状 |
| --- | --- |
| 应用指标（QPS/延迟/错误率/JVM） | ❌ **无**。没有任何 micrometer / prometheus 依赖 |
| 健康检查端点 | ❌ **无**。没有 actuator |
| 链路追踪 | ❌ **无**。没有 sleuth / zipkin / skywalking |
| 告警 | ❌ **无** |
| 日志聚合 | ❌ **无**。日志分散在各进程控制台 |
| 注册中心视图 | ✅ Nacos 控制台（能看到实例上下线） |
| 流量保护 | ✅ 网关 Sentinel 限流（**这是保护，不是监控**） |

> ⚠️ 不要把这套系统说成「有监控」。目前能做到的只是**被动排查**，
> 出问题后靠 §7 的手法定位，没有主动发现能力。

### 3.2 目前唯一的量化指标：网关 Sentinel

配置在 Nacos 的 `gateway-sentinel-flow-rules.json`：

| 路由 | 限流阈值 | 超限行为 |
| --- | --- | --- |
| `seckill-api` | 500 req/s | 返回 **429** + `{"success":false,"code":429,"msg":"网关：服务不可用"}` |
| `order-api` | 100 req/s | 同上 |
| `good-api` | 200 req/s | 同上 |

**运维含义**：日志里若出现 429，说明流量打到了阈值，
**不是故障而是削峰在生效** —— 但持续 429 意味着需要扩容。

### 3.3 建议接入项（若本项目继续演进）

按投入产出排序，**均为当前未实现**：

1. **Actuator**（成本最低）：各服务加 `spring-boot-starter-actuator`，
   暴露 `health` / `metrics` / `info`，`management.endpoints.web.exposure.include`
   按需开放。注意 `/actuator/**` **必须在网关白名单里单独处理**（当前会走 RBAC 判定被拒），
   建议只对内网开放而不经网关。
2. **Micrometer + Prometheus + Grafana**：Actuator 之上接 Prometheus 抓取，
   重点看网关的 `http_server_requests` 分位延迟、HikariCP 连接池使用率
   （**当前池大小是默认的 10，是最可能先撞上的瓶颈**）、JVM 堆与 GC。
3. **日志落盘 + 滚动**：见 §4.4。没有日志文件，前面这些接入都无从排查。
4. **链路追踪**：13 个服务 + 2 层 Feign 调用（order ↔ seckill 还是双向），
   排一个慢请求要翻多个服务的日志，接入后收益明显。

## 4 日志

### 4.1 现状

| 项 | 现状 |
| --- | --- |
| 日志框架 | Logback（Spring Boot 默认） |
| **配置文件** | ❌ **没有** `logback-spring.xml`，全用默认 |
| **`logging.*` 配置** | ❌ **一个都没有**（无 `logging.level`、无 `logging.file`） |
| 输出目标 | **仅控制台（stdout）**，不落盘、无滚动 |
| 日志级别 | 框架默认（root INFO），**无法从配置调整** |
| SQL 日志 | `mybatis.configuration.log-impl=StdOutImpl` → **每条 SQL 都打印到控制台** |
| 链路标识 | 无 traceId / MDC |

### 4.2 日志在哪里

- **13 个后端服务全部以 fat jar 启动**（2026-09-15 起不再依赖 IDEA），
  启动时用 `> D:\run-logs\<name>.log` 重定向，**日志都在 `D:\run-logs\`**。
- 一键启停：`deploy/windows/start_all_services.bat` / `stop_all_services.bat`。
- **单服务重启**：`deploy/windows/restart_service.bat <模块目录名> [日志名]`
  —— 改了某一个服务、不想等 70 秒全量重启时用。Nginx 重载：`deploy/windows/nginx_reload.bat`。
- **Nginx**：`D:\tools\nginx\logs\{mall,admin}.{access,error}.log`。

> ⚠️ **写启动脚本时注意**：`start "name" java ... > log 2>&1` 的重定向**管不到子进程**，
> 日志文件会是空的。必须把重定向写进子进程的命令行：
> `start "name" /min cmd /c "java ... > log 2>&1"`。
> 修好的样板见 `deploy/windows/restart_service.bat`（文件头的注释块解释了
> `cmd /c` 与 `PROGRA~1` 8.3 短名这两处坑）。

### 4.3 关键日志关键字速查

排查时直接在这些关键字上 grep：

| 关键字 | 出处 | 含义 |
| --- | --- | --- |
| `秒杀库存预热完成` | seckill-api | 预热写入成功 |
| `越权访问被拒绝` | 网关 | RBAC 判定为不通过（附 userId/path/method） |
| `非管理员令牌访问后台接口被拒绝` | 网关 | 会员令牌访问后台 |
| `RBAC 判定调用失败，按拒绝处理` | 网关 | **rbac-api 不可用**，请求被拒（503） |
| `order.close` / `order.dead.queue` | order-api | 超时关单消息链路 |
| `已参与过该秒杀或超出限购` | seckill-api | 业务码 7003 |
| `秒杀库存预热：当前没有进行中的秒杀活动` | seckill-api | **活动已过期**，预热停了（会连报 7004） |
| `超时关单兜底生效：命中 N 单` | order-api | **MQ 延时消息没送达**，兜底接住了 |
| `无法校验商品引用（商品服务不可用）` | brand/category-api | 调 good-api 校验失败，删除被 **fail-closed** 拒绝 |

> ⚠️ **`mybatis` 的 StdOutImpl 让日志极其嘈杂**，每条 SQL 都打。
> 排查时用关键字过滤，别直接翻。生产环境应先降级这一项（见 §4.4）。

### 4.4 建议改进（当前未实现）

```yaml

  level:
    root: info
```

## 5 备份与恢复

### 5.1 现状（重要）

| 数据 | 现状 | 风险 |
| --- | --- | --- |
| MySQL | **只有全量初始化脚本**，无备份、无增量、无时点恢复 | 数据丢失只能重建到种子状态 |
| Redis | **RDB 本来就开着**，2026-09-15 又开了 **AOF**（`everysec`），丢失窗口 ≤1 秒 | 已基本可控。**注意 Redis 跑在 WSL 里**，改配置要改 `/etc/redis/redis.conf`，不是 `D:\Redis\...`（见 `docs/部署文档.md` §3.2） |
| 上传目录 | `d:/shoplook2026/upload/` **在仓库外，无备份** | 商品图/轮播图丢失 |
| Nacos 配置 | 只有仓库里的模板，**真实密码在 `.local.yaml`（未跟踪）** | 配置丢失需重配 |

> ⚠️ `docs/sql/jifeng-mall-init.sql` **不是备份脚本** ——
> 它每张表都是 `DROP TABLE IF EXISTS` + `CREATE TABLE`，
> 执行会**清空现有数据**。切勿当作恢复手段用在生产库上。

### 5.2 MySQL 备份

```bat
REM 全量备份
mysqldump -uroot -p --single-transaction --routines --triggers ^
          --default-character-set=utf8mb4 shoplook2026 > backup_%date:~0,4%%date:~5,2%%date:~8,2%.sql

REM 恢复
mysql -uroot -p --default-character-set=utf8mb4 shoplook2026 < backup_20260915.sql
```

`--single-transaction` 保证 InnoDB 表的一致性快照且不锁表。
建议每日定时 + 保留 30 天，并把备份文件**存到另一块盘**。

### 5.3 Redis

**现状：RDB 本来就开着（发行版默认），2026-09-15 又开了 AOF（`appendfsync everysec`），
丢失窗口从「几分钟」压到「最多 1 秒」。**（此前文档写「没有任何持久化」是基于
`D:\Redis\...\redis.conf` 得出的 —— 而实际运行的是 **WSL 里的 Redis**，那份配置根本没被读取。
详见 `docs/部署文档.md` §3.2。）

如果持久化真的失效，后果按严重度排序：

1. **限购标记 `seckill:user:*` 丢失且不会重建** → 同一会员可以**重复抢购**同一商品。
   注意：库存键 `seckill:stock:*` 会被预热任务自动灌回，**限购键不会** ——
   这会造成「库存看着对，但限购失效」的错觉，很危险。
2. 登录失败计数丢失 → 已锁定的账号立即解锁（危害较小）。
3. 未支付订单的流水号映射丢失 → 影响关单回补（有 DB 兜底，危害中等）。

**建议**：开启 AOF（`appendonly yes`）或至少 RDB 定时快照，
并明确它属于**可重建状态**还是**权威状态** —— 本项目里限购标记是权威的
（DB 里没有对应记录），所以必须持久化。

## 6 定时任务与后台线程

系统里有三处。前两处**都是静默失败**，是最容易踩的运维坑；第三处是 2026-09-15 新加的兜底。

### 6.1 秒杀库存预热（seckill-api）

- **位置**：`SeckillStockPreheatTask`，`@Scheduled`，启动后 10 秒首次，之后每 60 秒。
- **可调参数**：`jifeng-mall.seckill.preheat-initial-delay-ms`（默认 10000）、
  `jifeng-mall.seckill.preheat-interval-ms`（默认 60000）。
- **策略**：
  - 活动**未开始** → 强制把 Redis 库存刷新为 DB 剩余库存；
  - 活动**进行中** → 仅在 key 缺失（Redis 重启/淘汰）时用 `SET IF ABSENT` 补齐，
    **绝不覆盖实时扣减结果**。这个设计是对的，运维上可以放心手工 `SET` 库存键。

> ✅ **原本的静默失败模式已于 2026-09-15 修复。**
> 原问题：`findActive()` 的条件是 `enabled = 1 AND end_time > now()`，
> **活动一旦过期，查询返回空集，任务直接 `return`，一行日志都不打**。
>
> 后果曾是：Redis 里 `seckill:stock:*` 消失、抢购全部返回 7004「已售罄」，
> 而日志里没有任何异常，只能靠「抢购失败」这个间接现象反推。
>
> **现在的行为**：活动集合变化时打日志（**边沿触发**，不是每 60 秒刷一行），
> 且服务启动后的第一次扫描**必定**打印一行，运维不用猜预热有没有在跑。
> 活动过期时会看到：
> ```
> WARN SeckillStockPreheatTask : 秒杀库存预热：当前没有进行中的秒杀活动（findActive 为空），
>   不再预热库存。若 Redis 中 seckill:stock:* 缺失，抢购将全部返回 7004。
>   请核对 seckill 表的 enabled / start_time / end_time（上一个活动集合=[1]）
> ```
>
> **排查动作**：先查活动时间窗，而不是查 Redis。
> ```sql
> SELECT id, name, start_time, end_time, NOW(),
>        (NOW() BETWEEN start_time AND end_time) AS is_active
>   FROM seckill WHERE enabled = 1;
> ```
> 续命：
> ```sql
> UPDATE seckill SET start_time = NOW() - INTERVAL 1 HOUR,
>                    end_time   = NOW() + INTERVAL 24 HOUR WHERE id = 1;
> ```
> 改完等一个预热周期（≤60 秒），或直接 `redis-cli SET seckill:stock:1 50` 立即生效。

### 6.2 超时关单兜底扫描（order-api）

- **位置**：`OrderTimeoutCloseTask`，`@Scheduled`，启动后 60 秒首次，之后每 60 秒。
- **可调参数**：

  | 参数 | 默认 | 含义 |
  | --- | --- | --- |
  | `jifeng-mall.order.timeout-close.scan-interval-ms` | 60000 | 扫描间隔 |
  | `jifeng-mall.order.timeout-close.initial-delay-ms` | 60000 | 启动后首次执行的延迟 |
  | `jifeng-mall.order.timeout-close.grace-ms` | 300000 | **宽限期**，见下 |
  | `jifeng-mall.order.timeout-close.batch-size` | 200 | 单批最多处理多少单 |

- **它兜的是什么**：待付款订单超时关闭的主路径是 RabbitMQ 延时消息
  （延迟队列 TTL → 死信队列 → `OrderCloseConsumer`）。这条路径是**单点**的 ——
  消息一丢，订单就永远停在「待付款」、库存永远不回补。触发条件很现实：
  投递时 order-api 不可用、消费端重试耗尽被丢弃（`max-attempts=3`）、
  MQ 重启丢消息、队列被误删。本任务就是这条路径的保险。

- **为什么有宽限期**：扫描的截止时刻是「订单超时 30 分钟 **+ 宽限期 5 分钟**」= 35 分钟，
  **比 MQ 的延时长**。这样正常运行全程由 MQ 处理、扫描空转；
  扫描只在「MQ 该到而没到」时动手。
  若两者都用 30 分钟，扫描会经常抢在消息之前关单，
  于是消费者每次都发现订单已不是待付款而打印「跳过」——主路径被架空、日志也分不清谁在干活。

- **日志语义**：
  - 没有超时订单 → **不打印**（这是正常稳态，打日志只会刷屏）；
  - 关闭了订单 → `WARN 超时关单兜底生效：命中 N 单（MQ 延时消息未送达），本次关闭 M 单`。

  > ⚠️ **看到这条 WARN 就说明主路径出问题了。** 它不是"正常工作"的日志，
  > 而是"MQ 延时消息没送到、兜底接住了"的告警，应当去查 MQ 消费端。

- **单批取满时会追加一条 WARN**（`单批已达上限 N，可能仍有积压未处理`），
  提示积压超过单批容量，需要人工介入。

- **并发安全**：本任务与 MQ 消费者可能同时处理同一单。
  `cancel()` 开头判 `status != 待付款` 直接返回 false，两条路径撞车只会有一边生效，
  **不会重复回补库存**（已实测：关闭后再扫一轮，状态与库存都不变）。

### 6.3 未使用图片清理（upload-api）

- **位置**：`UploadServiceImpl`，自建 `Executors.newScheduledThreadPool(10)`。
- **逻辑**：每次上传后注册一个 5 分钟延迟任务 —— 到时检查 Redis 里有无该 URL 的键，
  没有则删文件（即「已上传但未被业务引用的图片」）。
- **运维含义**：**上传成功不等于文件会保留**。业务方必须在 5 分钟内把该 URL
  写入 Redis，否则文件被删。这解释了「图片上传成功但过一会儿 404」的现象。

> ⚠️ **两个缺陷（当前未修）**：
> 1. 任务在**内存**里，**服务重启即全部丢失**，待删文件永久残留；
> 2. 任务体内**无 try/catch**，异常被 `ScheduledExecutorService` 静默吞掉，
>    无日志、无重试。
>
> 实测对照组：重启前 09:33 上传的文件一直留着；重启后 09:37 上传的 09:42 准时被删。
> 演示够用；生产应换成持久化延时任务（MQ 延迟队列或定时扫表）。

## 7 故障排查手册

按现象分类。**每条都是本项目实际出现过的问题。**

### 7.1 服务启动类

| 现象 | 根因与处置 |
| --- | --- |
| `Communications link failure` | MySQL 未启动；或 Nacos 配置里用了**模板的占位符密码**（`<你的MySQL密码>`）而非真实密码 |
| 启动即 `NoClassDefFoundError: XXX` | **用旧进程的命令行当 classpath 启动了新代码**。给服务加過依赖后，旧进程的 classpath 里当然没有该 jar。必须按当前代码重新解析 classpath |
| 启动报端口占用 | 上一个实例没退干净。先 `netstat -ano \| findstr :10015` 找到 PID 再 `taskkill /F /PID <pid>` |
| IDEA 里服务显示已停止但端口在监听 | 该服务是从 fat jar 启动的，不在 IDEA 里。见 `docs/部署文档.md` |
| `Unable to rename ... .jar to ... .jar.original` | **打包时服务还在运行，jar 被锁**。顺序必须是「先停服务 → 打包 → 再起」 |
| `Could not find the selected project in the reactor` | `mvnw -pl` 用了裸名字或相对路径。**必须用带冒号的 artifactId**：`-pl :jifeng-mall-spi` |

### 7.2 鉴权与权限类

> ⚠️ **先记住两种 403 不是一个东西**：
> **网关层拒绝 → 真实 HTTP 403**；**业务层 `BusinessException(403)` → HTTP 200 + body 里 `code=403`**。
> 写排查脚本时最容易在这里误判。

| 现象 | 根因与处置 |
| --- | --- |
| **所有后台接口 403，admin 也不例外** | ① RBAC 种子缺失（查 §7.6 的三个计数）；② **rbac-api 没起** —— 网关 fail-closed |
| **接口返回 503 而不是 403** | 网关**权限判定调不通**（rbac-api 不可用），或**目标业务服务未注册**。两者都返回 503，看网关日志区分：前者有 `RBAC 判定调用失败`，后者无 |
| 部分后台接口 403，部分正常 | 对应**资源行缺失**。资源 `2009~2020`（系统管理类）、`1007`+`2021`（地区管理）是后补的，从旧库升级时必须补 |
| 会员令牌能调后台接口 | RBAC 过滤器被改坏了。正确行为是：会员只能走白名单内的会员业务接口，其余一律 403 |
| 会员自助改资料/改密码 403 | 这两个接口**故意不在**网关的会员路径白名单里（裸 `PUT /api/members` 是后台接口）。会员应走 `/api/members/id/**` |
| 前台接口 401 | ① 令牌过期（admin 12h / member 7d）；② 该路径不在网关公开白名单里。注意**公开只对 GET 生效** |
| 登录返回 429 | 防爆破锁定（15 分钟 TTL），或网关 Sentinel 限流。前者提示里有剩余分钟数 |

### 7.3 秒杀类

| 现象 | 根因与处置 |
| --- | --- |
| 抢购全部返回 **7004 售罄** | ① **活动过期**（见 §6.1，最常见）；② Redis 里 `seckill:stock:*` 丢失。**先查活动时间窗，别急着查 Redis** |
| 抢购返回 **7003 已参与** | Redis 里有该会员的限购标记（**无 TTL**）。跑 `tools/verify/sql/reset_to_baseline.bat` |
| 抢购接口 200 但**订单永不生成** | MQ 消费端没进去。查 seckill-api 日志有无消费记录；**重点检查 `SeckillMqConfig` 的反序列化白名单** —— 新增消息类型没加白名单会导致 Spring AMQP 拒绝反序列化，**且发送端完全正常** |
| 订单取消了但**库存没回来** | 回补是 `try/catch` 包住的，失败只打 WARN，不重试、不回滚订单状态。实测后果是「订单已取消，但库存永久少 1」。触发条件很现实：order-api 先于 seckill-api 启动 |
| 取消订单后该会员仍不能再抢 | 老版本回补没释放限购标记（已修）。若仍有此现象，手工 `DEL seckill:user:{memberId}:{goodId}` |
| 库存数字对不上 | 见 §2.4 一致性核对 |

### 7.4 数据一致性类

| 现象 | 根因与处置 |
| --- | --- |
| `Column 'xxx' cannot be null` | **本项目出现 6 次的同一模式**：`insert` 语句显式列出全部列 → 数据库 `DEFAULT` **完全不生效** → 服务端不给值就是 null。**新增任何实体时，第一件事是逐个核对它的 NOT NULL 列有没有在 insert 前赋值** |
| 新增数据永远失败，但改、删正常 | 同上（NOT NULL 缺默认值只在新增路径暴露） |
| 支付/发货后状态不对 | 查状态机：`待付款 → 已支付 → 待收货 → 已确认`，退款单转「已取消」。非法流转返回 7005 |
| 正在退款的订单被发货了 | 老缺陷（已修）：`ship()` 只校验 `status == 已支付`，需额外判断退款在途 |
| 分类树接口 500 | 老缺陷（已修）：`buildTree` 只判 `parentId == null` 为根，而 DDL 是 `NOT NULL DEFAULT 0` |

### 7.5 消息队列类

| 现象 | 根因与处置 |
| --- | --- |
| 超时订单不关闭 | ① order-api 未启动；② 延迟队列积压未到点。查 `rabbitmqctl list_queues name messages`，`order.delay.queue` 的积压数 = **尚未到点**的消息数，用创建时间 + 30 分钟反推可确认某条消息是否已触发；③ 若扫描兜底也未生效，查 order-api 日志有无 `超时关单兜底` 的 ERROR |
| 日志出现 `超时关单兜底生效：命中 N 单` | **MQ 延时消息没送达**，兜底接住了。订单本身已被正确关闭（不用救），但要去查 MQ 消费端为什么不工作，否则每一单都要等 35 分钟才关 |
| 消息重试 3 次后被丢弃 | `listener.simple.retry.max-attempts=3`，耗尽即丢。查消费端日志的异常 |
| 关单消息二次投递导致重复回补 | 已有幂等保护（`cancel()` 开头判 `status != 待付款` 就 return）。若出现重复，查该方法是否被改坏 |

### 7.6 前端与 Nginx 类

| 现象 | 根因与处置 |
| --- | --- |
| 页面能开但所有接口 404 | Nginx `proxy_pass` **末尾多写了 `/`**，`/api` 前缀被截掉 |
| 刷新前端路由 404 | 缺 `try_files $uri $uri/ /index.html`（前端用 history 模式） |
| 两个前端相互覆盖样式/脚本 | 两个前端挂在了同一域名的不同子路径。Vite 产物用绝对路径 `/assets/`，必须分域名或分端口 |
| 图片 404 但上传接口返回 200 | ① 上传目录映射问题（`my.upload.location` 结尾必须带 `/`）；② 文件被 5 分钟清理任务删了（§6.2） |
| 图片地址是 `localhost` 打不开 | `my.upload.url-prefix` 写死了 `http://localhost:10020/upload`，**图片直连 upload-api 不走 Nginx**。换域名部署时必须改这一项 |
| 前端构建 OOM | `memory allocation of N bytes failed`。本机 16G 被 13 个服务占满，构建前先确认空闲内存 > 500MB，不够就停掉 vite dev server |
| WSL 里构建报 `Cannot find module '@rolldown/binding-linux-x64-gnu'` | `node_modules` 装的是 win32 原生绑定。**构建必须在 Windows 侧跑** |

## 8 变更与发布流程

1. **改代码前**：确认要改的模块 → 确认该模块对应的服务**是否在运行**（在运行会锁 jar）；
2. **停服务** → `mvnw package` 或 `mvnw -pl :模块 install` → **重启服务**；
3. **改前端**：Windows 侧 `npm run build` → 产物复制到 `D:/shoplook2026/web/<app>`；
4. **改配置**：改 Nacos 配置会**热生效**（各服务监听了配置），但**数据源类配置变更建议重启**；
5. **改网关或 Sentinel 规则**：网关路由与限流规则变更需**重启或刷新网关**；
6. **发布后验证**：跑 `tools/verify/` 下的对应脚本。
   **任何改动后至少跑一遍 `rbac_verify.py`（纯只读）与 `admin_verify.py`** ——
   本项目出现过两次「修 A 坏了 B」的回归（RBAC 修复导致会员改密 403）。
