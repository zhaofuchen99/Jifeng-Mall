## 1 部署形态与拓扑

采用**实机多进程部署**：13 个 Spring Boot 服务各占一个端口、由 Nacos 注册发现，
两个前端由 Nginx 托管静态资源并反向代理到网关。

```
                        浏览器
                          │
              ┌───────────┴───────────┐
              │                       │
        :8090 前台商城           :8091 后台管理
              │  Nginx 托管 dist 产物   │
              │  反代 /api 与 /upload    │
              └───────────┬───────────┘
                          │
                    :8888 网关（WebFlux）
                    ├─ 统一认证（JWT）
                    ├─ RBAC 越权判定（调 rbac-api）
                    └─ Sentinel 网关限流
                          │  lb:// 经 Nacos 负载均衡
   ┌──────────────────────┼──────────────────────┐
   │                      │                      │
 12 个业务服务（:10010 ~ :10021）
   │                      │                      │
 MySQL(3306)          Redis(6379)          RabbitMQ(5672)
                                              Nacos(8848) ← 注册与配置
```

> **关于容器化**：《开发流程指南》2.3 提到「后端服务集群容器化」。
> 本机未安装 Docker，容器化方案（Dockerfile / compose）**未包含在本交付物中**，
> 以保证交付内容全部经过实机验证。若需要容器化，第 6 章的 `mvn package`
> 产物本身就是可执行的 fat jar，容器化只是在其外面包一层基础镜像。

## 3 中间件部署

### 3.1 MySQL

1. 安装 MySQL 8.0，字符集设为 `utf8mb4`；
2. 建库导入（脚本自带 `CREATE DATABASE`，直接执行即可）：

```bash
mysql -uroot -p < docs/sql/jifeng-mall-init.sql
```

脚本会建 **23 张表** + 索引 + 演示种子数据（含 `admin` / `operator` / `member`
三个演示账号，密码均为 `123456`）。

> ⚠️ 脚本内**每张表都是 `DROP TABLE IF EXISTS` + `CREATE TABLE`**，
> 在生产库上执行会清空数据。只用于初始化或重建演示环境。

3. （建议）生产环境不要用 `root` 直连，建专用账号：

```sql
CREATE USER 'jifeng'@'localhost' IDENTIFIED BY '<你的密码>';
GRANT ALL PRIVILEGES ON shoplook2026.* TO 'jifeng'@'localhost';
FLUSH PRIVILEGES;
```

建完要同步改 Nacos 配置里的 `spring.datasource.username/password`（见 §5）。

### 3.2 Redis

1. 启动 Redis，确认 `PING` 返回 `PONG`；
2. 本机 Redis **未设密码**，因此 Nacos 配置里 `spring.data.redis.password` 留空。
   如果你的 Redis 设了密码，必须同步填上，否则秒杀相关服务启动即报认证失败。

> ⚠️ **本机实际用的是 WSL 里的 Redis，不是 Windows 那个。**
> 实测：`D:\Redis\redis-windows-8.8.0\` 下的 `redis-server.exe` **并没有在运行**；
> Windows 上 `127.0.0.1:6379` 是 `wslrelay.exe` 把请求转发进 WSL 的，
> 真正的服务端是 WSL 的 `/usr/bin/redis-server`（`config_file=/etc/redis/redis.conf`、
> `dir=/var/lib/redis`，systemd 单元 `redis-server`，`enabled`）。
>
> **为什么这条必须写清楚**：如果你照「Windows 版 Redis」去改 `D:\Redis\...\redis.conf`
> （比如开 AOF、设 maxmemory），改的是一个**根本没被读取的文件**，重启后毫无效果，
> 而排查时会一直以为配置生效了。判断依据用：
> ```bat
> D:\Redis\redis-windows-8.8.0\redis-cli.exe INFO server | findstr config_file
> ```
> 输出 `/etc/redis/redis.conf` 就说明连的是 WSL 那套。

Redis 承载的状态（排查问题时先看这里）：

| Key | TTL | 说明 |
| --- | --- | --- |
| `seckill:stock:{seckillGoodId}` | **无** | 秒杀库存，由 seckill-api 定时预热按 DB 灌入 |
| `seckill:user:{memberId}:{goodId}` | **无** | 限购标记，抢购成功后写入，回补时删除 |
| `seckill:order:{seckillNo}` | **无** | 流水号 → `seckillGoodId:memberId` 映射 |
| `login:fail:{audience}:{account}` | 15 分钟 | 登录失败计数（防爆破） |
| `c.s.s.*.ServiceImpl::*` | 1~30 天 | 三个服务的 Spring Cache（brand/category/region） |

**持久化现状（实测，2026-09-15）**：

| 项 | 值 | 说明 |
| --- | --- | --- |
| RDB | `save 3600 1 / 300 100 / 60 10000` | **本来就开着**（发行版默认配置）。崩溃最多丢几分钟的写入 |
| AOF | `appendonly yes`、`appendfsync everysec` | 2026-09-15 **新开启**，把丢失窗口从「几分钟」压到「最多 1 秒」 |
| `maxmemory` | `0`（不限制） | 因此**不会发生 key 淘汰**；策略 `noeviction` 也印证了这点 |
| 内存占用 | 1.25 MB / 10 个键 | 距上限很远 |

> ⚠️ **失持久化会丢什么**：`seckill:stock:*` 丢了会被预热任务按 DB 自动灌回（60 秒内），
> 但**限购标记 `seckill:user:*` 不会重建**（DB 里没有对应记录）——
> 表现为同一会员可以重复抢购。
>
> 若将来给 Redis 设了 `maxmemory`，**不要用 `allkeys-lru`**：
> 那会连无 TTL 的 `seckill:*` 一起淘汰。建议 `volatile-lru`
> （只淘汰带 TTL 的，即 Spring Cache 那批可重建的条目），
> 或保持 `noeviction` 让写失败暴露出来而不是静默丢数据。

### 3.3 RabbitMQ

1. 启动 RabbitMQ 服务，确认 5672 可达；
2. 默认账号 `guest/guest` 可用于本机；生产需新建账号并限制 vhost 权限；
3. （可选）开启管理插件，控制台在 15672：

```bat
rabbitmq-plugins enable rabbitmq_management
```

> ⚠️ **Windows 上以 LocalSystem 运行服务时**，`rabbitmq-plugins enable`
> 可能写到了用户目录（`C:\Users\<你>\AppData\Roaming\RabbitMQ`）而服务读的是
> `C:\Windows\System32\config\systemprofile\AppData\Roaming\RabbitMQ`，
> 两边不是同一个配置目录，导致控制台打不开。以 15672 是否监听为准判断。

用到的队列（全部由代码声明，无需手工创建）：

| 交换机 | 队列 | 用途 |
| --- | --- | --- |
| `seckill.order.exchange` | `seckill.order.queue` | 秒杀异步下单 |
| `order.delay.exchange` | `order.delay.queue` | 订单超时关单（TTL + 死信） |
| `order.dead.exchange` | `order.dead.queue` | 延迟消息到点后的死信消费端 |

> ⚠️ 排查「消息发出去但没人消费」时，注意 **seckill-api 的反序列化白名单**：
> `SeckillMqConfig` 给 `SimpleMessageConverter` 设了 `setAllowedListPatterns`，
> 新增消息类型必须同步加白名单，否则 Spring AMQP 会拒绝反序列化、
> 消费者方法根本不进入，且**发送端完全正常**（接口一直返回 200）。

### 3.4 Nacos

1. 以 **standalone** 模式启动：

```bat
cd /d D:\nacos\bin
startup.cmd -m standalone
```

2. 确认 8848 与 9848 都已监听（9848 是 3.x 的 gRPC 端口，缺它客户端连不上）；
3. 默认控制台 `http://localhost:8848/nacos`，账号 `nacos` / `nacos`（首次登录需改密码）。

## 4 数据库初始化

见 §3.1。初始化后**必须**核对 RBAC 种子数据完整，否则管理员会大面积 403：

```sql
SELECT (SELECT COUNT(*) FROM t_rbac_resource)       AS res,   -- 期望 28
       (SELECT COUNT(*) FROM t_rbac_perm)           AS perm,  -- 期望 6
       (SELECT COUNT(*) FROM t_rbac_perm_resource)  AS pr;    -- 期望 28
```

这三个数字是**功能必需**，不是装饰：
- 资源 `2009~2020`（后台用户/角色/用户组/权限/资源/菜单/四张关联表/秒杀商品/订单明细）
  —— 缺了管理员访问「系统管理」整个模块全部 403；
- 资源 `1007` + `2021` + 权限 `306`（地区管理 FR-210）
  —— 缺了后台点「新增/编辑/删除区划」全部 403。

## 5 Nacos 配置发布

**这一步最容易出错，且出错后现象是「服务起不来」而不是「配置不对」。**

### 5.1 建命名空间

控制台 → 命名空间 → 新建。**命名空间 ID 必须手填 `jifeng-mall`**
（Nacos 默认生成 UUID，要手工改成这个值）。group 也需要是 `jifeng-mall`。

> 为什么 ID 必须固定：14 个 `application.yaml` 里全部写死了
> `namespace: jifeng-mall`。若用自动生成的 UUID，需要全局替换这些文件。

### 5.2 发布两个 dataId

源文件在 `jifeng-mall-api/docs/远程配置/`：

| dataId | 格式 | 内容 |
| --- | --- | --- |
| `jifeng-mall-common.yaml` | YAML | 数据源、Redis、RabbitMQ、MyBatis、PageHelper |
| `gateway-sentinel-flow-rules.json` | JSON | 网关限流规则（seckill 500/s、order 100/s、good 200/s） |

> ⚠️ 仓库里的 `jifeng-mall-common.yaml` 是**模板，密码是占位符**（`<你的MySQL密码>` 等），
> 直接发布会 MySQL 认证失败。本机真实值在**未被 git 跟踪**的
> `jifeng-mall-common.local.yaml`（`.gitignore` 已忽略 `*.local.yaml`）。
> 发布时用那一份，或按模板逐项填好自己的密码。

### 5.3 配置项分工

理解这个分工能省很多排查时间：

| 配置 | 位置 | 原因 |
| --- | --- | --- |
| `server.port`、`spring.application.name` | 各服务本地 `application.yaml` | 服务自身属性 |
| **Nacos 连接参数**（`config.server-addr`、账号、namespace、group） | 各服务本地 `application.yaml` | 先有鸡还是先有蛋：拉不到远程配置就起不来 |
| `discovery.server-addr` | **Nacos 公共配置** `jifeng-mall-common.yaml` | 12 个服务的 discovery 块里只写了 `port` |
| 数据源 / Redis / RabbitMQ / MyBatis / PageHelper | Nacos 公共配置 | 全项目单一来源 |
| 网关路由表、Sentinel 规则 | 网关本地 yaml + Nacos JSON | 网关不引入公共配置 |

> ⚠️ 因此**公共配置里的 `spring.cloud.nacos.discovery` 段不能删**，
> 删了 12 个服务就无法注册（但能启动，表现为网关转发 503）。

## 6 后端构建与启动

### 6.1 打包

```bat
cd /d <项目根目录>
set JAVA_HOME=C:\Program Files\Java\jdk-25.0.4
mvnw.cmd -DskipTests clean package
```

产物是 13 个可执行 fat jar：

| 服务 | 端口 | 端口 | 服务 |
| --- | --- | --- | --- |
| brand-api | 10010 | 10016 | cart-api |
| category-api | 10011 | 10017 | order-api |
| good-api | 10012 | 10018 | user-api |
| member-api | 10013 | 10019 | rbac-api |
| member-address-api | 10014 | 10020 | upload-api |
| region-api | 10015 | 10021 | seckill-api |
| gateway-webflux | 8888 | | |

启动：

```bat
java -Dfile.encoding=UTF-8 -jar jifeng-mall-api\jifeng-mall-brand-api\target\jifeng-mall-brand-api-1.0.0.jar
```

> ⚠️ **只改一两个模块时不要跑全量 `package`**：正在运行的 jar 会被锁住，
> repackage 一步必失败（`Unable to rename ... .jar to ... .jar.original`）。
> 顺序永远是「先停服务 → 打包 → 再起」。只改个别模块时用：
>
> ```bat
> mvnw.cmd -o -DskipTests -pl :jifeng-mall-spi,:jifeng-mall-region-api install
> ```
>
> 注意 `-pl` **必须用带冒号的 artifactId 写法**，裸名字和相对路径都会报
> `Could not find the selected project in the reactor`。

### 6.2 一键启停（推荐）

仓库里带了四个脚本，**13 个服务全部以 fat jar 运行，不依赖 IntelliJ IDEA**：

```bat
cd /d <项目根目录>\deploy\windows
start_all_services.bat                          REM 启动全部（约 70 秒）
stop_all_services.bat                           REM 停止全部
restart_service.bat jifeng-mall-order-api       REM 只重启一个（先停后启）
nginx_reload.bat                                REM 重载 Nginx 配置
```

- `restart_service.bat` 的参数是**模块目录名**（即 `jifeng-mall-api\` 下的目录名），
  第二个参数可选，用来指定日志名，缺省与模块名相同。停进程靠匹配命令行里的模块名，
  所以参数必须写全。**改完 jar 要先停服务再 install**，否则 Maven repackage 会报
  `Unable to rename ... .jar.original`。

- 启动顺序写死为「参照数据 → 业务服务 → **网关最后**」，
  且每个服务间隔 5 秒 —— 避免 13 个 JVM 同时初始化。
- 日志统一到 `D:\run-logs\<name>.log`。
- 脚本里的 `ROOT` / `JAVAEXE` 两个变量按你的环境改。

> ⚠️ **为什么强调「不依赖 IDEA」**：在 2026-09-15 之前，13 个服务里有 12 个是从
> IDEA 的 Run 配置启动的 —— **关掉 IDEA 就全停**，机器重启后要手工点 13 遍。
> 那不算部署。现在全部走 fat jar，IDEA 只是编辑器。

### 6.3 手工启动单个服务

```bat
java -Dfile.encoding=UTF-8 -jar jifeng-mall-api\jifeng-mall-brand-api\target\jifeng-mall-brand-api-1.0.0.jar
```

若要手工按顺序起，参照：先 `rbac-api` / `user-api` / `member-api` / `region-api` /
`member-address-api` / `brand-api` / `category-api` / `good-api` / `cart-api` /
`order-api` / `upload-api` / `seckill-api`，**最后起网关**。

> `seckill-api` 与 `order-api` 互相 Feign 调用，两者都启动功能才完整。

> 属于正常现象，后起的服务起来后会自愈。

## 7 前端构建与 Nginx 部署

### 7.1 构建

两个前端工程各自构建，产物在各自的 `dist/`：

```bat
cd /d <项目根目录>\mall-web  && npm install && npm run build
cd /d <项目根目录>\admin-web && npm install && npm run build
```

> ⚠️ **必须在 Windows 侧构建**。`node_modules` 里装的是 win32 的 rolldown
> 原生绑定，在 WSL 里 `npm run build` 会崩在
> `Cannot find module '@rolldown/binding-linux-x64-gnu'`。
>
> ⚠️ 构建对内存敏感。本机 16G 被 13 个 Java 服务占满时，Vite 的 Rust 打包器
> 会 `memory allocation of N bytes failed`。构建前先确认空闲内存：
> `wmic OS get FreePhysicalMemory`（单位 KB，建议 > 500MB），
> 不够就先停掉 vite dev server（**注意 `taskkill` 要杀 `node.exe`，
> 杀 bash 包装进程没用**）。

### 7.2 发布到 Nginx 目录

```bat
xcopy /E /Y /I mall-web\dist  D:\shoplook2026\web\mall
xcopy /E /Y /I admin-web\dist D:\shoplook2026\web\admin
```

### 7.3 Nginx 配置

配置文件：`deploy/nginx/nginx.conf`（仓库内），部署到 `<nginx>\conf\nginx.conf`。

关键点（都是实测中确认过必须这么写的）：

| 配置 | 为什么 |
| --- | --- |
| `try_files $uri $uri/ /index.html` | 两个前端的 router 都是 `createWebHistory`。刷新 `/goods/1` 这类前端路由时磁盘上没有对应文件，不回退就是 404 |
| `proxy_pass http://jifeng_gateway;` **末尾不带 `/`** | 路径原样透传（`/api/goods?x=1` 到网关还是它）。网关和业务服务的 controller 都依赖 `/api` 前缀，加了 `/` 会被截掉 |
| **两个 server 用两个端口** | Vite 产物默认 `base='/'`，`index.html` 引用绝对路径 `/assets/xxx.js`。两个前端挂同一域名的 `/mall` 与 `/admin` 下会争抢 `/assets/` 互相覆盖。生产上应分配两个域名，或给其中一个改 `base` 后重新构建 |
| `/assets/` 长缓存 + `index.html` 不缓存 | Vite 产物带内容哈希可长缓存；`index.html` 缓存了会让用户拿到旧的文件名清单 |
| `/upload/` 也反代到网关 | 上传接口路径无 `/api` 前缀，容易漏配 |

> ⚠️ **不要用 `expires 30d;` + `add_header Cache-Control` 同时写**：
> 两者都会发 `Cache-Control` 头，会发出两个同名头。只用 `add_header` 写全。

### 7.4 启动与自检

```bat
cd /d D:\tools\nginx
nginx -t                先语法自检
start nginx             启动
nginx -s reload         改配置后重载
nginx -s quit           停止
```

自检清单（每一条都对应一个真实故障模式）：

```bat
curl -I http://localhost:8090/                      应 200 text/html
curl -I http://localhost:8090/goods/1               应 200（SPA 回退生效）
curl    http://localhost:8090/api/goods?pageNo=1&pageSize=3
                                                    应返回统一 JsonResp
curl -I http://localhost:8090/upload/banner/banner-1.png
                                                    应 200 image/png
```

## 9 常见问题

| 现象 | 原因与处置 |
| --- | --- |
| 服务启动即报 `Communications link failure` | MySQL 没起，或 Nacos 配置里的密码与实际不符（用了模板没填真密码） |
| 服务启动即 `NoClassDefFoundError` | 用旧进程的命令行当 classpath 启动了新代码。classpath 要按当前代码重新解析 |
| 网关转发返回 503 | 目标服务未注册。查 Nacos 服务列表；注意**公共配置里的 discovery 段是否被误删** |
| 所有后台接口 403，`admin` 也不例外 | RBAC 种子缺失，或 **rbac-api 没起**（网关 fail-closed，判定不出来就拒绝，返回 503） |
| 后台部分接口 403，部分正常 | 对应资源行缺失，见 §4 的三个数字 |
| 秒杀接口一直 7004 售罄 | 活动过期（预热任务静默退出）或 `seckill:stock:*` 丢失。续命 SQL 见 `tools/verify/README.md` §五 |
| 秒杀接口一直 7003 已参与 | Redis 里有该会员的限购标记（无 TTL）。跑 `reset_to_baseline.bat` |
| 上传的图片 5 分钟后消失 | upload-api 的「未被引用的图片定时清理」在生效 —— 这是设计行为。上传后业务方需在 5 分钟内把该 URL 写入 Redis，否则文件被删 |
| 图片上传成功但打不开 | 检查 `my.upload.location` 结尾的 `/`（缺了 Spring 会把最后一段当文件名）与 `UploadWebMvcConfig` 的静态映射 |
| 前端能打开但所有接口 404 | Nginx 的 `proxy_pass` 末尾多写了 `/`，`/api` 前缀被截掉 |
