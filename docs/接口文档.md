> 本文档依据《详细设计说明书 V1.0.2》第 4/8 章，并结合当前后端实现整理。供前端（PC 商城 / 后台管理系统）对接使用。所有接口经网关统一暴露。

| 项目 | 说明 |
| --- | --- |
| 网关地址 | `http://网关IP:8888`（开发环境） |

| 数据格式 | 请求与响应均为 JSON |

# 1 通用约定

## 1.1 统一响应结构

```json
{
  "code": 200,
  "success": true,
  "msg": "success",
  "data": { }
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| code | int | 状态码，200 成功，其余见错误码 |
| success | boolean | 是否成功 |
| msg | string | 提示消息 |
| data | object/null | 业务数据 |

## 1.2 分页约定

- 请求参数：`pageNo`（默认 1）、`pageSize`（默认 0 = 查询全部）
- 响应 `data` 为 `PageInfo`：

```json
{
  "code": 200, "success": true, "msg": "success",
  "data": {
    "list": [ "..." ],
    "total": 36,
    "pageNum": 1,
    "pageSize": 12
  }
}
```

## 1.3 认证

- 除「公开接口」外，请求头需携带 `Authorization: Bearer {token}`
- 网关解析令牌后向后端注入请求头（业务服务使用）：
  - `X-User-Id`：用户/会员主键
  - `X-User-Name`：登录账号（user 为 username，member 为 account）
  - `X-Audience`：admin / member

## 1.4 错误码

| code | 含义 |
| --- | --- |
| 200 | 成功 |
| 400 | 参数错误 |
| 401 | 未登录或令牌失效 |
| 403 | 无权限 |
| 404 | 资源不存在 |
| 429 | 请求过于频繁/限流；登录失败次数过多被临时锁定 |
| 500 | 系统内部错误 |
| 7001 | 库存不足 |
| 7002 | 未到秒杀时间或已结束 |
| 7003 | 已参与过该秒杀/超出限购 |
| 7004 | 秒杀已售罄 |
| 7005 | 订单状态不允许该操作 |

# 3 前台接口清单（PC 商城 / 会员端）

## 3.1 会员认证

### 会员注册（公开）
```
POST /api/members/register
请求：{ "account": "member01", "password": "123456", "name": "张三", ... }
响应 data：LoginUserInfo
```

### 会员登录（公开）
```
POST /api/members/login
请求：{ "account": "member01", "password": "123456" }
响应 data：
{
  "token": "<JWT>",
  "userId": 1,
  "account": "member01",
  "name": "张三",
  "audience": "member"
}
```

> **失败锁定（需求 6.2 / NFR-002）**：同一账号连续失败 **5** 次后锁定 **15** 分钟，
> 期间即使密码正确也返回 `code=429`（如 `登录失败次数过多，账号已锁定，请 14 分钟后重试`）。
> 登录成功即清零计数。账号**不存在**同样计数，否则可据「有没有被锁」枚举出真实账号。
> 后台登录（4.1）行为完全一致。

## 3.2 商品

| 功能 | 方法 | 路径 | 参数 | 权限 |
| --- | --- | --- | --- | --- |
| 商品分页 | GET | `/api/goods` | keyword、categoryId、brandId、priceLow、priceHigh、sort(priceAsc/priceDesc)、isHot、pageNo、pageSize | 公开 |
| 商品详情 | GET | `/api/goods/id/{id}?full=true` | full=true 含品牌/分类 | 公开 |
| 分类树 | GET | `/api/categories/tree` | — | 公开 |
| 首页热销 | GET | `/api/goods?isHot=1` | — | 公开 |
| 首页轮播 | GET | `/api/goods/banners` | `enabled=true`（只取启用中）、pageNo、pageSize（0=全部） | 公开 |

> **首页轮播（需求 5.3 / FR-102）**。首页按需求要展示「可配置图片与跳转链接」的轮播，
> 但**详细设计说明书通篇没有给轮播建模**——2.4 节的微服务清单是 13 个（12 api + 网关）、
> 3.3 节没有对应的表、8 节的接口清单里也没有轮播接口。为不擅自新增服务（那会与设计文档的
> 服务清单冲突），**轮播并入商品中心 good-api**，路径挂在 `/api/goods/banners`：
> 首页的另一块数据（热销商品）本来也由它提供，而且这样能直接复用网关已有的两条规则
> ——「GET `/api/goods/**` 公开」与商品管理权限资源 `/api/goods/**`，不必改网关白名单、
> 也不必往 `t_rbac_resource` 补行。
>
> ⚠️ 代价：网关的公开规则是**按前缀**的，所以 `GET /api/goods/banners`（后台列表，含停用项）
> 对游客也开放。轮播本身就是公开内容，被看到一条停用项没有实际影响，因此接受。
> 若将来轮播里要放未发布的活动信息，应把它挪到独立路径（如 `/api/banners`）并单独注册权限资源。

首页取轮播的写法：

```
GET /api/goods/banners?enabled=true&pageNo=1&pageSize=0
响应 data.list：[ { id, title, imageUrl, linkUrl, sortNo, enabled } ]   // 已按 sort_no, id 排序
```

- `imageUrl` **可能为空**：为空或图片失效时前台渲染渐变兜底，不会破图。
- `linkUrl` 可能是站内路由（`/goods`、`/seckill`）或 `https://` 外链；为空表示不跳转。
- 图片文件本身走 `/upload/banner/*.png`，见 `docs/首页轮播图来源.md`。

### 退款详细定义（模拟，需求 FR-206 / 详细设计 5.5.2）

退款与模拟支付对称，同样分「发起 / 确认」两步，退款状态 `refund_status` 才有「退款中」这个中间态可观察：

```
# 1) 发起退款：无退款 → 退款中（订单状态不变，仍是「已支付」或「待收货」）
PUT /api/orders/{id}/refund
响应 data：true

# 2) 确认退款：退款中 → 已退款；订单转为「已取消」并回补库存
PUT /api/orders/{id}/refund/confirm
响应 data：true
```

| 环节 | 允许的订单状态 | 允许的退款状态 |
| --- | --- | --- |
| 发起退款 | 已支付 / 待收货 | 无退款（或 `refund_status` 为 NULL） |
| 确认退款 | 不限 | 退款中 |

- 状态字典里没有「已退款」这个**订单**状态，所以退完订单落到终态「已取消」，
  是不是退款单由 `refundStatus=已退款` 区分（前端也据此展示）。
- 任一步骤状态不符，统一返回 `code=7005`。
- 库存回补与取消订单同一套逻辑：**秒杀单**回补秒杀库存（Redis + `seckill_good.stock/sold`，
  并释放该会员的抢购名额），**普通单**按订单明细回补 `good.qty`。
- 后台操作人记入 `order.updated_by`（需求 7.5-3 审计）。

## 4.9 地区

读接口公开（前台收货地址的省市区三级联动要免登录可用），写接口走 RBAC（资源 `/api/regions/**`）。

```
GET    /api/regions                 —— 分页列表（pageSize=0 取全量，前台组树用）
GET    /api/regions/id/{id}         —— 单条（含父级）
GET    /api/regions/parent-id/{id}  —— 子级列表（id 传 0 取省级）
POST   /api/regions                 —— 新增
PUT    /api/regions                 —— 修改
DELETE /api/regions   body: [id,…]  —— 批量删除
```

写接口的三个约定（都由 region-api 强制，客户端传什么都不作数）：

- **层级由上级推导**：根为 1，其余为父级 +1，最深 3 级（省/市/区），
  第四级返回业务错误 400。请求体里的 `level` 一律被忽略。
- **`id` 就是行政区划编码**：新增时可显式传（如 `440000`），留空则自增；重复编码返回 400。
  修改时不可改动（主键）。
- **修改时 `parentId` 缺省表示"不动父级"**，传 `0` 才是移到根；
  把节点挂到它自己或它的下级下面会被拒（400），移动后其后代的 `level` 会同步修正。
- **删除是级联的**：删省级会连同下级的市/区一起删掉，`data` 返回实际删除行数
  （大于传入的 id 个数），不是 `1`。

# 5 关键流程（供前端参考）

## 5.1 登录认证流程

```
1. 前台：POST /api/members/login 或 /api/users/login → 获得 token
2. 后续请求头携带 Authorization: Bearer {token}
3. 网关校验令牌，非法/过期返回 401 → 前端跳转登录并回跳原页面
```

## 5.2 下单流程

```
1. 确认购物车/立即购买 → POST /api/orders/create（需登录）
2. 返回待付款订单 + orderNo
3. POST /api/orders/{id}/pay → 模拟收银台
4. POST /api/orders/{id}/pay/confirm → 已支付
5. 待付款订单 30 分钟未支付 → 网关/服务端自动关单并回补库存（RabbitMQ 延时消息）
```

## 5.3 秒杀流程

```
1. 查看秒杀活动 → GET /api/seckills/active / /api/seckill-goods/seckill/{id}
2. 点击立即秒杀 → POST /api/seckills/grab（需登录）
3. Redis Lua 原子扣减（防超卖）+ 记录已抢（防重复）
4. 发 RabbitMQ 异步下单 → 返回 orderNo
5. 前端凭 orderNo 轮询 GET /api/orders/member-account/{account} 查看订单生成并支付
6. 秒杀订单 30 分钟未支付自动关闭，回补秒杀库存
```

> ✅ **秒杀库存一致性（已实现）**
> - **防超卖（双保险）**：Redis + Lua 原子扣减；DB 侧成交时以条件更新兜底
>   `UPDATE seckill_good SET sold=sold+qty, stock=GREATEST(stock-qty,0) WHERE id=? AND stock>=qty`
>   （异步下单消费者执行，库存不足则不成交，防超卖）
> - **抢购登记**：抢购成功将 `seckill:order:{seckillNo} = {seckillGoodId}` 写入 Redis
> - **异步下单幂等**：消费者与 order 服务均以 `seckillNo` 为准，同一秒杀流水号仅创建一张订单，MQ 重投不重复下单 / 不重复扣减；下单失败自动回滚本次扣减后重试
> - **超时关单回补**：秒杀订单超时（30 分钟）由 order 服务关单；order 检测 `seckillNo` 非空时调用秒杀服务 `POST /api/seckills/restock`，同步回补 Redis 秒杀库存 `seckill:stock:{seckillGoodId}` 与 `seckill_good.stock/sold`；秒杀订单**不**回补普通商品库存 `good.qty`（下单时未扣减）
> - **库存预热**：秒杀服务定时任务扫描启用且未结束的活动，将各秒杀商品剩余库存预热到 `seckill:stock:{seckillGoodId}`——活动未开始强制刷新，进行中仅缺失时补齐（不覆盖实时扣减）；间隔见 `jifeng-mall.seckill.preheat-interval-ms`（默认 60 秒），另保留首抢懒加载兜底

## 5.4 退款流程（模拟，后台操作）

```
1. 后台在订单列表找到「已支付」或「待收货」的订单 → 发起退款
   PUT /api/orders/{id}/refund        → refund_status：无退款 → 退款中
2. 核对后在订单列表 → 确认退款
   PUT /api/orders/{id}/refund/confirm → refund_status：退款中 → 已退款
                                         订单状态 → 已取消
                                         回补库存（秒杀单回补秒杀库存并释放名额）
3. 会员在「我的订单 / 订单详情」看到「已退款」
```

> **退款在途的订单不再参与履约**：`退款中` / `已退款` 的订单一律不能再发货（`PUT /ship`）、
> 也不能再确认收货（`PUT /confirm`），都返回 `code=7005`。
> 发起退款后订单状态仍是「已支付」，不加这道判断，正在退款的订单会被发出去。
> 重复点「发起退款」或「确认退款」同样被状态机拦下——退款不会退两次。
