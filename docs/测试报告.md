## 3 测试方法与工具

- 全部为**黑盒接口测试**，通过 HTTP 与真实部署交互，不 mock、不直连数据库断言。
- 脚本位置：`tools/verify/`，使用方式见同目录 `README.md`。
- 每个脚本用 `check(名称, 条件, 详情)` 记录断言，收尾打印
  `合计 N 项：通过 X，失败 Y`，失败项逐条列出，进程退出码反映成败。
- **数据隔离**：临时账号与业务数据统一带前缀（`fe_own_` / `bench_` / `lg_test_` /
  `mrp_test_` / `adm_test_` / `REG_TEST` / `BANNER_TEST`），断言与清理都按前缀识别，
  不写死自增主键。

### 3.1 可复现性

测试结论可复现的前提是**每轮从同一状态出发**。因此配套了一个重置脚本：

```
tools/verify/sql/reset_to_baseline.bat
```

它同时重置 MySQL 与 Redis。**只重置 MySQL 是不够的** —— 秒杀状态有一部分只存在
Redis 里（`seckill:stock` / `seckill:user` / `seckill:order`），SQL 够不着。
早期版本的压测脚本正是漏了这一步：上一轮留下的限购标记（**无 TTL**）会让下一轮
抢购全部返回 7003，表现为「库存明明重置了却抢不到」。该问题已修复，
重置脚本现在会自检并在失败时以非零码退出，不会出现「报成功但没清干净」。

### 4.1 覆盖到的关键业务规则

以下规则各有独立断言，不是「跑通即通过」：

- **状态机**：订单 `待付款 → 已支付 → 待收货 → 已确认` 四个接口全通；
  非法流转（如已确认订单再取消）返回业务码 7005。
- **退款状态流转**：`无退款 → 退款中 → 已退款` 两步式，中间态可观察；
  重复发起 / 重复确认被拒；待付款订单不能退。
- **库存回补精确到件**：普通订单回补 `good.qty`、秒杀订单回补
  `seckill_good.stock/sold` 并释放抢购名额。
- **默认地址唯一性**：同一会员仅一条 `is_default=1`。
- **购物车 save-merge**：同商品重复加入数量累加而非新增行。
- **层级不变量**（FR-210）：区划 `level` 由上级推导、最深三级、改父级时
  后代层级同步修正、不能挂到自己的下级（成环检测）。
- **缓存失效**：品牌/分类/地区的查询带 `@Cacheable`，写操作后立即读回必须是新值
  （地区为 30 天 TTL，不清缓存会长期读到旧数据）。

## 5 接口测试结果

接口契约以 `docs/接口文档.md` 为准，本节记录**文档与实现不一致**之处 ——
这些是联调中最容易踩的坑，已在文档中更正或注明：

| 项 | 文档 | 实现 | 处置 |
| --- | --- | --- | --- |
| 商品列表筛选 | 写了 `keyword` / `priceLow` / `priceHigh` / `sort` | `GoodSearchBean` 不支持，前端在前端做 | 已在 README「待完善」注明 |
| 地区树接口 | 详细设计 4.5 写 `GET /api/regions/tree` | 实现是 `/api/regions/parent-id/{id}` | 以实现为准，接口文档按实现写 |
| `GET /api/regions/id/{id}` | 「含父级」 | SQL 未 join，`parent` 返回 null | 已在接口文档标注 |
| `GET /api/orders/id/{id}` 对不存在的订单 | 未写明 | 返回 **HTTP 200 + `data: null`**，而不是 404（该 controller 直接 `JsonResp.success(findById(id))`，没走 `requireOrder`；而 cancel/pay 等路径会抛 404） | 已记录。**同资源不同接口的状态码语义不一致**，属既有设计瑕疵；判断"订单存在与否"要看 `data` 是否为 null |
| 统一响应 | — | 业务失败也是 **HTTP 200** + body `code`；只有网关的 401/403/429/503 才是真实 HTTP 状态码 | 已在 `tools/verify/README.md` 提示 |

> ⚠️ **写断言时最容易错的一点**：网关层拒绝 → 真实 HTTP 403；
> 业务层 `BusinessException(403)` → **HTTP 200 + body 里 code=403**。
> 本项目联调中出现过一次「断言写成 `status == 403`」导致的假失败 ——
> 被测代码是对的，测试写错了。**测试脚本本身也会有 bug。**

## 6 性能测试（秒杀并发）

完整报告见 `docs/秒杀压测报告.md`。摘要：

### 6.1 场景

库存 50、200 个会员各抢一次，分并发度 10 / 50 / 100 / 200 四轮。
**洪峰轮用 `threading.Barrier` 让 200 个请求同一瞬间发出** ——
不同步的话只是排队，考验不到 Redis Lua 的原子性。

### 6.2 结果

**正确性（四轮全部通过）**：成交数恒为 50、DB `sold`=50、`stock`=0、
50 个流水号去重后仍 50、无非预期错误。**无超卖、无少卖、无重复下单。**

**性能**：

| 并发度 | 吞吐 | P50 | P95 | P99 |
| --- | --- | --- | --- | --- |
| 10 | 684 req/s | 14 ms | 19 ms | 21 ms |
| 50 | 672 req/s | 41 ms | **75 ms** | 88 ms |
| 100 | 576 req/s | 66 ms | 139 ms | 198 ms |
| 200（同步洪峰） | 386 req/s | 349 ms | 420 ms | 436 ms |

**对 NFR-001（抢购提交 P95 < 100ms）**：并发 ≤ 50 达标，并发 ≥ 100 不达标。

延迟随并发近似线性上升，而单笔 P50 仅 14ms —— 说明瓶颈在**请求排队**
而非单笔处理。本机是单实例 + 客户端同机竞争 CPU 的开发环境。

### 6.3 实测的复现性边界（重要）

2026-09-15 用同一脚本、同一参数（200 路栅栏同步）重跑，得到
**P95 = 541ms、吞吐 287 req/s**，与 2026-09-12 的 420ms / 386 req/s
相差约 **29%**。

这**不是回归**，而是同一台机器上多跑了一个 Nginx、系统整体负载不同所致的抖动。
它本身就是一条结论：**这些数字的精度不足以支撑生产容量规划**，
只能用于横向对比与验证正确性。生产性能须在独立压测机上以集群形态重测。

### 6.4 未覆盖

1. 单机单实例，未验证多实例集群下的负载均衡与库存竞争
2. 客户端与服务端同机，CPU 互相争抢，绝对延迟偏高
3. **只压了抢购提交接口**，未压 MQ 消费、异步下单、`decreaseStock` 的吞吐上限
4. 未做长时间稳定性测试（4 轮短时压测）
5. 未测超时关单与库存回补在高并发下的表现（单笔已验证，未做批量）
6. Redis / MySQL / RabbitMQ 均为默认配置，未做参数调优
7. 未测活动开始瞬间的缓存预热竞争

## 8 缺陷记录

测试过程中发现并修复的缺陷，按类型分组。**这些是本报告最有分量的部分** ——
它们说明测试真的在起作用，而不是走了一遍流程。

### 8.1 NOT NULL 列未赋值（出现 6 次，同一模式）

`insert` 语句显式列出每一列 → 数据库的 `DEFAULT` **完全不生效** →
服务端不给值就是 `Column 'x' cannot be null`。全部只在「新增」路径上暴露。

| 表 | 未赋值的 NOT NULL 列 | 后果 |
| --- | --- | --- |
| `order` | `is_del` | 秒杀下单必失败 |
| `order` | `total_pay` | **普通下单从未成功过**（金额要遍历完明细才算得出，代码却先 save） |
| `rbac_role` / `rbac_group` | `enabled` | 后台新增角色/用户组必失败 |
| `seckill_good` | `sold` | 后台新增秒杀商品必失败 |
| `user` | `login_times` / `enabled` / `status` / `locked` | 后台新增后台用户必失败 |
| `good` | `is_del` / `is_hot` / `is_take_down` / `is_seckill` | 后台新增商品必失败（`is_del` 最隐蔽：后台表单里根本没有这个字段） |

### 8.2 密码未加密直接入库（同型两处）

`user-api` 与 `member-api` 的 `save`/`update` 直接透传 mapper，只有 `register`
走加密。后果：通过接口创建/修改的账号**密码明文入库且永远登录失败**。
（`member` 表甚至没有 `locked` 列，所以防爆破的锁定状态改放 Redis。）

### 8.3 权限体系失效（三处互相掩盖）

1. **RBAC 调用根本发不出去**：`WebClient.baseUrl()` 填了服务名却没有负载均衡能力，
   解析失败 → 异常被 `onErrorReturn(true)` 吞掉 → **永远放行**。整个过滤器是死代码。
   修复前零授权账号 `operator` 能读 **14 个后台接口**的数据。
2. **失败放行**：鉴权查询失败时放行，等于关掉权限校验。已改为 fail-closed，
   但用 **503** 而不是 403，把「权限服务不可用」与「你确实没权限」区分开。
3. **会员令牌畅通无阻**（修①后才暴露）：原判断是「非 admin 就放行」，
   任何会员拿着合法令牌就能调后台全部接口。

配套还补了资源 `2009~2020` 的种子数据 —— 只修网关不补数据，
管理员访问系统管理会全部 403。

### 8.4 越权与归属（修好网关后才暴露的下一层）

网关修好后才发现：会员可以按 id 读**他人**订单（含收货人姓名、电话、地址）、
订单明细和会员资料；购物车主键自增，遍历 id 就能读改删他人购物车；
下单时传他人 `cartId` / `addrId` 能把别人的购物车下成自己的订单。
修法是在 **controller 层**加归属校验（不放 service —— service 同时被 MQ
消费者等系统路径调用，它们没有「请求者」概念）。

### 8.5 消息与缓存

| 缺陷 | 现象 | 根因 |
| --- | --- | --- |
| 秒杀订单消费者从未执行 | 接口一直 200，但订单永不生成 | `SeckillMqConfig` 缺反序列化白名单，Spring AMQP 默认拒绝反序列化应用自定义类，重试耗尽后丢弃。**发送端完全正常**，极易漏测 |
| 分类树必炸 | `GET /api/categories/tree` 从未成功过 | `buildTree` 只判 `parentId == null` 为根，而 DDL 是 `NOT NULL DEFAULT 0` |
| 上传接口 200 但图片打不开 | 文件真落盘了 | upload-api 没有静态资源映射，`DispatcherServlet` 找不到 handler 被兜底吞成 500 |
| 秒杀名额不随订单回补 | 订单取消后库存回来了，但该会员 24 小时内不能再抢 | 回补只删库存键，没删限购标记 |

### 8.6 状态机漏洞

**退款在途仍可发货**：`refund()` 只改 `refund_status`、不动 `order.status`，
而 `ship()` 只校验 `status == 已支付` —— 不加判断就会把正在退款的订单发出去；
`待收货` 的退款单同理还能被会员「确认收货」，确认后订单是终态「已确认」，
退款一确认又要翻成「已取消」，状态机自相矛盾。

> 这个缺陷是**写设计文档时发现的** —— 把流程描述一遍，漏洞自己就浮出来了。

### 8.7 其它

- **网关白名单漏项**：`/api/seckill-goods/**` 未列入公开路径，
  游客打开首页/秒杀会场取不到秒杀商品列表（401）。
- **会员自助改资料被 403**：这是修 RBAC 时引入的**回归** ——
  会员改资料调的是后台的裸 `PUT /api/members`。修法不能简单放行该路径
  （那样任何会员都能 `PUT {id: 别人的id, password:x}` 接管账号），
  而是改走已放行的 `/api/members/id/**` 前缀并加 `assertSelf` 归属校验。
- **种子商品图为坏链**：种子里的 `/upload/good/iphone.png`、`mate.png`
  项目里并不存在，商品图一直是坏的。

## 9 已知限制

1. **性能数据不适用于生产容量规划**（见 §6.3、§6.4）。
2. **安全自查有四项未自动化**（见 §7.2），其中支付验签**在模拟实现下无从谈起**。
3. **测试数据会污染演示环境**，必须靠重置脚本回收。重置脚本
   `reset_to_baseline.bat` 里的数据库连接信息与路径是**本机专属**，
   换机器需先改那三个变量。
4. **秒杀活动会过期**：过期后预热任务静默退出、Redis 无 `seckill:stock:*`
   且**不留任何日志**，排查很隐蔽。续命 SQL 见 `tools/verify/README.md`。
5. **脚本断言的是当前实现的行为**，不是需求的绝对真值。实现变更需同步改断言。
6. **未做浏览器端 UI 测试**：所有断言都走 HTTP 接口，前端页面只做了人工确认。
   前端构建产物可编译（`vite build` 通过），但页面渲染、交互、
   响应式布局没有任何自动化覆盖。
